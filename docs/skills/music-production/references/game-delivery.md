# 循环与游戏交付

## 先选择播放结构

| 需求 | 音频与运行时方案 | 必须核实 |
|---|---|---|
| 整首循环 | 开头与末尾共同组成闭环 | 前奏若在文件里，每轮都会重播 |
| 前奏仅播一次 | 独立intro接loop，或播放器支持明确循环区间 | 实际调度、解码、采样边界与切换；只交单一整曲loop不能实现 |
| 状态切换 | 明确分段或可组合分层，按拍或约定边界切换 | 相位、节拍、调式、余音、交叉淡化与状态恢复 |
| 非循环音乐 | 正常音乐性收束 | 不为通过loop指标改写结尾 |

只改音频即可满足需求时保持现有逻辑；确需独立前奏或适应性调度时，核工程能力后在已授权范围实现，不凭设计稿宣称运行时已支持。

在Unity中，单个AudioSource开启loop会循环整个AudioClip。一次性前奏通常用独立intro和loop片段、两个声源按音频时钟提前调度，主体声源开启循环；尾音需要重叠时保留其播放空间。只在每帧检测结束后换clip或跳转位置不能保证无缝。若必须单声源，先核实循环区间/自定义读取等实际实现能力，再决定方案。

## 三种连续性分别检查

**音乐连续性**：末句与首句的音高/和声、乐句间距、密度、音区和动态能否接续。过长近静音可能像停播重启，强尾折回可能让首次进入突兀；有意休止可以保留，说明音乐作用。

**信号连续性**：保留跨边界音符与混响的合理延续；周期处理的首尾增益一致。可用周期渲染、适当重叠或符合素材的方式。强行端点归零会掩盖跳变但可能造成能量凹陷；周期混响也不自动解决和声不连续。

**播放器连续性**：核导入、重采样、编码延迟、Streaming/解码和实际循环行为。离线PCM平滑仅证明文件层面；运行时与目标设备未测就记未测。首播与循环续播都要覆盖。

## 混播与格式

响度目标依据用途、对白/SFX、平台和用户偏好确定；一次案例的−29LUFS、44.1kHz、PCM或声道数不是通用标准。区分导出响度、引擎音量和Mixer增益。关注静音后回升、旁白避让和必要提示音的可辨识度。

Unity项目核实际AudioClip引用和导入配置。替换使用中资产时保留原`.meta` GUID，核采样率/声道/压缩/归一化/加载方式是否符合本项目；不为单次音频修改统一改全工程设置。其他引擎遵从其真实资源标识与播放机制。

## 交付内容按请求选取

- 正式音频与版本化试听；保留原版本便于回退。
- 需要继续制作时，提供可复现工程或脚本、乐谱/事件、源映射、种子与参数；分轨统一起点/长度，注明干湿和处理阶段。
- 来源、许可与署名；有损源、合成音或替代乐器据实标注。
- 实际验证报告、文件哈希、播放/导入连接和剩余试听项。

只制作音频不自动包含上传、发布、联系他人或改无关设置。技术验收与主观听感分别记录。
