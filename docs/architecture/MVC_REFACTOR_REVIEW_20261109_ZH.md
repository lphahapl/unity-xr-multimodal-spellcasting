# MVC 重构方案二次审阅与优化取舍

状态：设计审阅完成，修订提案待实施批准；没有重构运行代码。任务：ARCH-MVC-REVIEW-20261109。核查日期：2026-11-09（Asia/Shanghai）。

## 判断

原方案对玩家数据归属、SkillController 生命周期、玩家自身反馈和 v2 兼容的判断成立；已包含双模型原子提交、训练场冷却和准备态屏障，不能把这些当成遗漏再次批评。真正需要收紧的是：迁移中间版本如何保持唯一权威、准备态怎样证明就绪，以及领域依赖如何在编译层闭合。

建议保留方向，缩小每次施工单位。先把一条用户操作从数据、命令、保存到 UI 完整迁通，再扩大范围。以下是静态设计风险，并不表示已经在现有游戏复现这些重构故障。

## 优化后的实际接口

对调用方保持三个小入口：玩家命令负责成长/伤害/恢复，SkillController 负责施法及取消，保存协调者负责检查点。UI 读取展示数据和结果，拿不到完整主控或可变 DTO。PlayerObj 拥有玩家状态与反馈接线，具体声音/视觉算法仍封装在内部。

`TryCast(request) -> CastResult` 应返回请求身份、接受/拒绝及稳定原因；接受表示资源与施法实例已确认，不等于已经命中或已经发射。教学按对应事实区分“成形”“发射”“命中”。准备句柄与资源撤销只在技能模块内部，外部无需理解这些步骤。

最小的深模块标准是：新增一种技能不修改玩家存档协调和腕匣内部；调整脚步不修改关卡音乐；改存档格式不修改伤害公式。若拆类只增加转发、调用方仍要掌握整个对象图，应合回内部实现。

## 首个切片与退出依据

1. P0 冻结当前首章/P1/训练场、存档副本、配置和已知失败。记录实际写入者/消费者；不改运行行为。
2. 首片只迁技能知识/永久解锁/等级、物品、货币及奖励收据的运行归属；同步迁对应成长命令、旧章节适配、保存映射与 UI 读取。旧章节尚存时，其完成入口通过同一用例提交新玩家状态与旧章节状态，不能把旧 DTO 留作另一权威。
3. 用“激活铜叶→一次成长→UI刷新→写盘失败保留内存→重试→重新载入”证明完整闭环；拒绝购买不扣钱，重复奖励不重领。兼容适配的写入目标逐项列出。
4. 首片通过后接 HP/MP/CD，P3 再换技能执行协议。首个技能选火球闭环；护盾、剑各自保留既有算法与当前参数。

这不是增加第二套大框架：不新增完整 DI、通用事务、通用状态树、联网权威或按每个子状态各造三层 MVC。普通内部类能解决的事留在模块内部。CSV 的八列保留，具体消费者/字段切换清单由 P0 读取真实引用后形成，不能在设计审阅中伪造已完成清单。

## 必须补跑的失败用例

| 触发 | 可观察结果 |
|---|---|
| 准备中缺失必要资源、TryArm明确失败、准备两次释放 | 无扣费/CD/伤害/成功通知/占用泄漏；清理幂等 |
| 刷新旧盾失败；可选护盾视觉缺失 | 前者保留旧盾和本次资源；后者数值成功且只记录视觉故障 |
| 接受通知中请求恢复/切段/再施法 | 新命令进入下一命令阶段，不嵌入本次提交；表现监听异常不退款 |
| 同会话重建玩家实体后重送旧命中，或旧加载回调到达 | 旧命中不再次结算；旧代次不能写当前模型；不清零账本绕过数量上限 |
| 落点准备成功但模型拒绝；恢复中发生加载失败 | 保持旧状态，或停在明确加载门控；不返回可操作的半恢复状态 |
| v2 写失败后再次成长并切片回滚 | 最新已提交快照重试；回滚匹配代码/资产/测试数据，不覆盖用户后续正式档 |

这些是实施验收条目，本轮没有执行 Unity、Play、APK 或头显测试。原 14/51 项结果仍只是历史基线。
