# 连续结印序列：实现评估与日志风险

日期：2026-11-04。状态：分析与提案，未实现序列匹配，未修改业务代码、配置或场景。

## 结论

当前框架可以扩展连续多印。效果执行、法力、冷却和投掷可以继续复用，主要工作在输入配方、动作分段、序列匹配和冲突校验。最难的是从连续评分中划分可靠的“一次印”，以及阻止旧证据、短暂过渡姿态和共享前缀误触发。仅把 `sealName` 换成数组不够。

第一版建议精确有序匹配 2～3 印，以增量状态机实现；先约束冲突配方，不同时加入漏印容错、任意跳印或模糊序列。这里的印数是首轮验收范围建议，不是引擎硬限制。

## 需要优先处理的风险

### SEQ-01：短保持与稀疏采样的判定

当前日志中的模板保持为 0.070 秒，`maximumSampleGap` 为 0.120 秒。[Observe](../../Assets/scripts/logic/Skills/Core/SkillMatchEngine.cs) 以首末样本时间差累计保持，未额外要求最少有效样本数。因此两个合格样本相隔 0.100 秒时，按当前判定即可完成 0.070 秒保持。这是源码可推导的边界，不是日志已证实的误施法。

序列版建议要求“稳定时长 + 足够的新鲜样本”，分别配置进入/退出条件，并限制可累计的相邻间隔。短暂低分只能有限等待，等待期不计入合格保持；无效追踪、必需特征缺失和明显长断帧不能平滑成有效输入。具体保持时长、样本数和容忍时间需录制后调参，暂不统一抬高所有阈值。

### SEQ-02：动作必须分段，同一印不能按帧重复计数

目前 `Evidence` 按单配方保存，组合模式还会滚动更新其 Start/End；它不是不可变的多印事件流。序列应使用独立 episodeId，保存时间、印、质量、配置版本及 Epoch，并在完成时冻结本段证据。

`[子,子]` 必须检测有效退出再进入，不能把持续保持计成两个印；`[子,丑,子]` 中稳定的丑应形成明确的分段边界。当前 0.150 秒退出计时比 0.070 秒保持长，不能直接沿用为所有快速换印的唯一切段条件。追踪丢失不代表玩家主动退出，当前组合技能的“持续同印重新就绪”也不能直接当作序列里的第二个同印。

### SEQ-03：共享前缀、错误印和一次性消费

若纯结印 A 技能是 `[子]`，B 技能是 `[子,丑]`，A 立即释放就会抢走 B 的起始输入。当前校验仍比较单个 `sealName`，需要改为完整配方校验。

第一版建议禁止同一激活上下文中有歧义的终止前缀；以后需要允许时，再明确选择延迟短配方、语音限定或显式确认。候选可以暂时共享未消费的前缀，选出唯一完整路径后才统一消费其全部 episodeId；取消和玩法门禁则按策略清掉整条候选，防止残余步骤补发。

短暂 Unknown 可以作为换印间隔，稳定识别出的错误印不能任意跳过，否则 `[子,错误印,丑]` 会被当作 `[子,丑]`。重试应基于明确的前缀回退规则，并保持路径时间顺序、连续性与不同 episode，不拼凑不相干片段。

### SEQ-04：整条序列的时间窗口与取消边界

继续使用：`max(口令结束, 最后一印结束) - min(口令结束, 第一印开始) <= W`。增加独立的换印间隔上限；不能每完成一印就重新给整个技能 8 秒。当前 10 秒历史与 2 秒语音延迟预算支持最多 8 秒组合窗，扩展前必须同时检查缓存容量和实际采样率。

模式切换、移动占用、暂停、菜单、取消和输入重置必须处理候选进度及 Epoch。短丢帧时可以在总超时内保留已经确认的步骤，但当前未完成的保持重新累计；长丢失是否整条作废应成为明确规则，不能恢复追踪后自动跳到下一印。手槽和法力可用于提前反馈，最终效果激活仍由原 RPG 准入链结算。

## 算法与性能改动顺序

1. **先做可靠动作分段。** 接收质量通过的评分事实，输出有限容量的印事件流；保持“未知”“歧义”“追踪无效”三种不同原因。适度迟滞减少阈值附近来回切换，不能用滤波掩盖长时间错误输入。
2. **再做增量序列状态机。** 少量配方逐个保存下一步索引、起止时间和 episodeId 路径即可。每个新事件只推进有关候选，避免每帧遍历整个骨骼历史、排列组合地寻找路径。配方多、前缀大量共享以后，再考虑前缀树；暂不需要用复杂的时序学习模型替换现有手印评分。
3. **优化高频评分与分配。** [SealProfile.cs](../../Assets/scripts/data/SealLab/SealProfile.cs) 当前每次 Evaluate 创建 SealScore、RuleScore，ValidateRules 创建 HashSet，规则逐个线性查找 featureId；可在配置加载时编译为整数索引，复用数值数组，详细诊断按需生成。[匹配器](../../Assets/scripts/logic/Skills/Core/SkillMatchEngine.cs) 也逐帧校验模板、扫描竞争分数并复制骨骼；后续可缓存配置校验结果、按阈值语义共用印判定、预计算最高和次高有效竞争分数。配置修改须更新版本并失效缓存，不能缓存失效模板。这些是热点候选，当前没有 Profiler 数据证明它们导致了日志里的长帧。
4. **保留诊断能力并限制成本。** 增加 `episode_started/completed`、`sequence_advanced/reset`、`input_gap` 结构化事件，记录前两名得分、覆盖率、fresh/version、重置原因和完整配方 ID。仅短时主动录制逐样本数值用于回放，不长期每帧输出骨骼 JSON；原始骨骼缓存是否缩减需先确认回放与重算用途。

## 验收建议

先用两到三种容易区分的印，覆盖正常顺序、错误顺序、稳定错误中间印、短暂 Unknown、快速过渡、同印重复、共享前缀、口令先后与迟到、断帧、模式切换、手槽占用和冷却。标注玩家预期动作，分别统计完成耗时、误触发、漏步骤、重置原因、主线程耗时与 GC 分配。

建议实施范围：扩展 `SkillDefinition`、`SkillRecipeInfo` 和配置校验；拆出动作分段与序列匹配模块；接入控制器取消/提示和回放检查。效果定义、伤害、护盾与投掷继续复用。旧单印资产作为长度 1 配方兼容，不能直接删掉旧字段导致资产迁移丢失。

本次只静态审阅当前源码并解析历史日志，没有运行新的 Unity 性能采样、模拟多印测试或头显录制。现行架构设计文档中的多印/K-N 容错仍是规划，本提案的精确匹配首轮范围尚未替代原设计。
